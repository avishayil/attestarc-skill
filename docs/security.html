A security model for a skill that learns

AttestArc consults versioned platform facts — a knowledge plane — that change what a finding means. Once a tool can learn facts that alter verdicts, one equation governs everything:

Poison the knowledgeTeach it a dangerous pattern is “safe.”
=
Compromise the logicSuppress a real finding — no repo access needed.

So AttestArc treats its knowledge plane as security-critical code, and the pipeline that produces it as a software supply chain to be defended.

The primary rule

Nothing learned at runtime may modify the trusted security brain. AI may discover, propose, and propose changes to itself — but a deterministic trust policy decides what becomes trusted, and the running assessor can never grant itself more trust.

Three trust zones

The reasoning corpus is partitioned by trust — enforced in code (verify-gated reads, no network in the assessor, a non-writable kernel) and process (reviewed PRs into a protected main, eval-gated, SHA-pinned Actions).

Kernel · always loaded

The reasoning kernel

SKILL.md, core/, the verification helpers, the schemas, the eval corpus.

Changes only through reviewed, eval-gated PRs; root-of-trust files call for two parties. Never writable by the running skill during an assessment.

Candidate knowledge · untrusted

Everything not yet verified

LLM extractions, web/changelog deltas, researcher and user claims. The model produces only a candidate — no self-declared status, confidence, or authority.

MAY shape which questions get asked. MUST NOT change a conclusion.

Three principals

Skill modes plus a development workflow — not a hosted multi-agent runtime. The assessment path and the network-facing update path are separated so a malicious repository can never become an exfiltration channel.

Assessor

/attestarc

  • Read repo & verified knowledge
  • Write findings.json
  • Reach the network
  • Write kernel/knowledge or self-grant trust

Updater

/attestarc knowledge refresh

  • Fetch allow-listed sources
  • Write candidate knowledge; promote per policy
  • Access the target repository
  • Write the kernel; sign/publish releases

Evolver

dev-time

  • Read candidates/evals
  • Propose branch changes + evals
  • Write the production skill; release
  • Modify/delete trusted evals in the same step

Attestation-anchored updates

The root of trust is an external anchor (knowledge/trust-anchor.json) that ships outside any bundle — so a bundle can never declare its own trust. It pins the Sigstore build-provenance identity (repo + workflow + the reviewed git ref + OIDC issuer). Verification shells out to gh attestation verify.

verify_download

Updater · network / gh

  1. Identity matches the anchor — workflow path + artifact-specific ref (bundle ⇐ knowledge-v tag, revocation ⇐ main) + issuer.
  2. Manifest pack hashes match; no undeclared pack.
  3. Fresh — short TTL, freeze protection.
  4. Version > recorded highest_version.
  5. prev_digest chains to the high-water head — required once installed.
  6. Not revoked.

ANY failure → DISCARD, keep LKG.
All pass → eligible. It decides; it mutates nothing.

verify_installed

Assessor · no network / gh

  1. In-package snapshot? → yes: bootstrap-trusted (integrity only).
  2. Otherwise → trusted only if client state records this exact version + digest was attested.
  3. Pack hashes match; no undeclared pack; not revoked.
  4. Else → untrusted; dependents route to needs_review.

Never fetches — verifies against recorded client state.

Defends against, with trust identity-constrained (an attestation for another repo/workflow doesn't satisfy the anchor) and anti-rollback judged against the client's own memory (~/.attestarc/state/), never the bundle:

tampering rollback to vulnerable freeze on stale forged bundle mix-and-match packs malicious mirror

Installing the package

The skill package itself has a separate root of trust — bootstrap-anchor.json, outside the shipped payload. Be precise about what you get:

No crypto claim

git clone of a signed tag

Git checks out the ref; it does not verify the tag's SSH signature unless you run git verify-tag. Fully supported (still runs the in-package integrity + trust-contract gate) — but makes no claim about who produced the package.

Cryptographic check

install.py --from-tarball

gh attestation verify against bootstrap-anchor.json (repo + issuer + release-skill.yml@refs/tags/v<semver>) before extracting, then safe-extracts only verified contents. Attested under an exact-HEAD gate. Fail-secure: any gap aborts with nothing extracted.

Fail-secure, and a kill switch

The runtime never fetches-then-trusts. Every anomaly degrades to one of a few safe responses — uncertainty always routes to needs_review, never “ask the LLM what seems reasonable.”

Kill switch

Attest the revocation record → Roll back to a re-verified LKG → Re-observe affected findings

The internal caller-trusts-me apply has no public entry point, so a forged revocation can't become an attacker's rollback primitive — and a tampered retained snapshot is never silently reinstated.

How trust is created

Trust is never asserted — it is produced by two deterministic pipelines and consumed by an offline assessor. Below, the components are the process; the text is only a hint.

Workflow 1

Candidate → Verified · the promotion pipeline

1
Allow-listed source

Fetch adapter records requested URL, final URL & redirect chain — the model never supplies raw bytes.

Gate · quarantine receipt

Stored by content hash; resolving re-hashes the bytes & re-checks the final URL — a forged receipt won't resolve, a cross-origin redirect is rejected.

2
Candidate

Model output only — no status, confidence, or self-declared authority. Helpers emit facts, not verdicts.

Derive · authority ← URL registry

Re-derived by classifying the source URL; a candidate that self-declares a different authority is rejected.

Derive · direction ← git diff

A lowering, uncertain, or additive edit of an active entry → review. Never read from a model field.

3a
Auto-promote

Requires a digest-bound eval-result (candidate + baseline + corpus). A bare {passed:true} or recycled result never counts.

3b
Human review

Recorded approver. Evals are additive-only — a change can't delete the test that catches it.

Gate @ release · verify-promotions

Recomputes every active entry from pinned inputs; a hand-edited pack can't ship.

Verified knowledge

Drives a conclusion only after the verify-gate.

Workflow 2

Reviewed commit → Installed trust · release & attestation

1
Reviewed commit on main

PR-reviewed; root-of-trust files need two parties.

Gate · exact-HEAD

The tagged commit must be the tip of main — not mere ancestry — so an old commit can't be retagged as a higher version.

2
Sign & attest · Sigstore

Artifact-specific ref: a bundle ⇐ its knowledge-v tag, a revocation ⇐ main — neither can impersonate the other.

3
External anchor

The pinned identity ships outside the bundle, so a bundle can never declare its own trust.

4
verify_download · Updater

Identity + pack hashes + freshness + monotonic version + prev_digest chain + not-revoked. Any failure → discard, keep LKG.

5
install

verify → safe-extract → re-verify → semantic gate → atomic commit. The one path that advances trust.

Gate · integrity ≠ conformance

A matching hash proves only “released bytes.” validate_snapshot must also pass — at install and every read.

Verified last-known-good

Trusted only if the client's own memory records this exact version + digest was attested; otherwise the in-package bootstrap.

Workflow 3

Assessment → findings → re-observation

1
Assessor · offline, read-only

No network; reads verified knowledge only through the verify-gate.

2
Findings {id, content_hash}

A secret-like value is fingerprinted for audit — but if it looks like a secret the hash is withheld (recoverable from its sha256).

Gate · knowledge change

Never auto-resolves a finding.

requires_reverification → re-observe

A read-time view; the actual condition is re-observed, never silently mutated.
