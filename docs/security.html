A security model for a skill that learns

AttestArc consults versioned platform facts — a knowledge plane — that change what a finding means. The moment a tool can learn facts that alter verdicts, poisoning its knowledge becomes equivalent to compromising its logic.

Teaching AttestArc that a dangerous pattern is “safe” would suppress a real finding without ever touching the target repository. So AttestArc treats its knowledge plane as security-critical code, and the pipeline that produces it as a software supply chain to be defended. This page explains, transparently, how that works — and what is novel about it.

The primary rule. Nothing learned at runtime may directly modify the trusted security brain. AI may discover knowledge, propose knowledge, and propose changes to itself — but a deterministic trust policy decides what becomes trusted, and the running assessor can never grant itself more trust.

Three trust zones

AttestArc's reasoning corpus is partitioned by trust. The kernel/knowledge boundary is enforced in code (the assessor reads knowledge only through a verify-gate, its helpers contain no network code, the kernel is not writable during an assessment) and in process (reviewed PRs; two-party review for root-of-trust files).

Kernel · highly trusted · always loaded

The reasoning kernel

SKILL.md, core/ (methodology, severity, evidence, agent-safety, promotion-policy…), the verification helpers, the schemas, and the eval corpus.

Changes only through reviewed PRs, gated by the eval corpus; root-of-trust files need two-party review. Never writable by the running skill during an assessment.

Verified knowledge · trusted for reasoning

The knowledge plane

Attested, versioned, temporal, provenance-backed packs (knowledge/). Refreshed by the Updater, never by the Assessor.

Drives a conclusion only after the verification chain passes; the in-package snapshot is bootstrap-trusted because it rode in on the signed release.

Candidate knowledge · untrusted

Everything not yet verified

LLM extractions, web and changelog deltas, researcher claims, user feedback, conflicting evidence. The model produces only a candidate (no status/confidence, no self-declared source authority); those trusted fields are assigned by promotion, never the model.

MAY influence which investigation questions are asked. MUST NOT change a security conclusion. Becomes verified only by passing deterministic promotion policy.

Three principals

The assessment path and the network-facing update path are separate principals with disjoint capabilities — skill modes plus a development workflow, not a hosted multi-agent runtime. The separation is structural and documented: the assessor path simply contains no fetch step, and ingestion lives upstream. The Assessor and Updater are separated precisely so a malicious repository cannot turn the assessment path into a network-egress or exfiltration channel.

Attestation-anchored updates

The root of trust is an external anchor (knowledge/trust-anchor.json) that ships inside the SSH-signed skill release and lives outside any downloaded bundle. It pins the Sigstore build-provenance identity (repo + signer workflow + the reviewed git ref + OIDC issuer) an official bundle must have been produced under — the identity check binds the certificate's trailing @<ref>, not just the workflow path, so an attestation minted from an unreviewed branch is rejected — and a bundle can never declare its own trust. Verification shells out to the system gh attestation verify (no crypto dependency of our own). There are two entry points, and they are deliberately asymmetric:

verify_download

Updater · network / gh

  1. gh attestation verify the archive and the manifest — identity matches the anchor (repo + workflow path + git ref + issuer)?
  2. Manifest pack hashes match, and no undeclared pack sits in the tree.
  3. Fresh — short TTL, freeze protection.
  4. Version > the client's recorded highest_version.
  5. prev_digest chains to the installed last-known-good.
  6. Not revoked.

ANY failure → DISCARD the download, keep the LKG.
All pass → eligible to install. verify_download decides; it mutates nothing.

verify_installed

Assessor · no network / gh

  1. Is the root the in-package snapshot?
    → yes: bootstrap-trusted (integrity only).
    → no: trusted only if client state records this exact version + digest was attested.
  2. Manifest pack hashes match, and no undeclared pack.
  3. Not revoked.
  4. Else → untrusted; affected chains route to needs_review.

The assessor never fetches; it verifies against recorded client state.

This defends against knowledge tampering, rollback to vulnerable knowledge, a freeze on a stale version, a forged bundle, mix-and-match of files (the attestation covers the manifest, which pins every pack), and a malicious mirror. Trust is identity-constrained: a valid attestation for some other repo/workflow does not satisfy the anchor. Anti-rollback is judged against the client's own persistent memory (~/.attestarc/state/trusted-state.json), never a value inside the bundle.

Verify → install → persist. Advancing the high-water mark is done by exactly one path — install — so a bundle can never verify while state is left half-advanced. It verifies the archive's own attestation before extracting it, then safe-extracts the archive (refusing absolute paths, .., and symlink/hardlink members before writing anything, and extracting member-by-member rather than extractall), re-verifies the staged bytes, atomically renames the snapshot into place, and only then atomically advances client state. Rollback memory (~/.attestarc/state/) and installed snapshots (~/.attestarc/knowledge/snapshots/) live in separate directories, and a corrupt — not merely absent — client-state file fails closed: the Updater refuses to advance and the assessor falls back to the in-package snapshot until an explicit reinit.

Fail-secure, and a kill switch

The runtime never fetches-then-trusts. On any anomaly it degrades safely — and uncertainty always routes to needs_review, never to “ask the LLM what seems reasonable.”

Kill switch. A compromised knowledge version can be revoked. The single public revocation path (verify_and_apply_revocation) attests the revocation record against the anchor exactly like a bundle, records the revoked version(s), rolls the active snapshot back to the most recent retained non-revoked one (or the in-package bootstrap when none remains), and marks findings assessed under it requires_reverification. Because the internal caller-trusts-me apply has no public entry point, a forged revocation cannot become an attacker's rollback primitive — and it re-observes affected findings rather than silently resolving them. This path is designed before it is needed.

What's novel here

A trust-split brain

The security-relevant reasoning corpus is partitioned Kernel / Verified / Candidate, and the boundary is enforced in code and process — not in prompt text.

Verification is a fact, not a verdict

The helpers emit checks and facts; they never render a security judgment. Verified knowledge drives conclusions only after the verify-gate; candidate knowledge only shapes questions.

Derived, not asserted, authority

A source's authority is re-derived by reclassifying its URL through an identity-scoped registry. A candidate that self-declares its authority is rejected if it disagrees.

An external attestation anchor

The pinned Sigstore identity lives outside every downloadable bundle, so a bundle can never declare its own trust. It binds the workflow path and the git ref, and the release workflow refuses to sign a commit that isn't contained in reviewed main (an ancestry gate) — so provenance can't be minted from an unreviewed ref. Sigstore build-provenance replaces a homemade role protocol.

Bootstrap vs verified-LKG

The in-package snapshot is bootstrap-trusted; a refreshed one is trusted only if the client's own out-of-band memory records that exact version + digest was attested.

Direction over confidence

A high-authority source proposing a security-negative or merely uncertain change still gets human review. The direction is derived from the claim's effect and its diff against the last released snapshot — never read from a model-controlled field — and an additive edit of an active entry routes to review even without an explicit supersede.

Self-verifying quarantine receipts

Fetched documents are stored by content hash with a receipt binding the object to derived provenance, and treated as inert data — never as instructions. Resolving a receipt re-hashes the stored bytes and re-classifies its final URL, so a fabricated receipt does not resolve and a cross-origin redirect is rejected. Every promotion-eligible source must carry one.

The eval corpus is root-of-trust

A knowledge change may add paired find/refuse evals but can never weaken or delete a trusted eval in the same step — a poisoning change cannot also delete the test that catches it.

Findings bound by content hash

Findings record {id, content_hash} dependencies; a superseded fact surfaces requires_reverification as a read-time view — never a silent mutation, never an auto-resolve.

Integrity ≠ conformance

A matching attested pack hash proves only these are the released bytes. Before it drives a conclusion, a snapshot must also pass validate_snapshot: every entry schema-valid, every source's authority matching the registry's classification of its URL, no secret-looking value — checked at install and on every read.

Not even a hash of a secret

A secret-like injection attempt is fingerprinted for audit, but if the text looks like a secret the hash is withheld — a low-entropy secret is recoverable from its sha256, so only a redaction marker is stored.
